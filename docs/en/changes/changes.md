#### OAP Server
* Fix the Cilium fetcher dropping or double-reading Cilium nodes. The Peer notify stream, the cluster watcher and the 10-second refresh timer rebuilt the shared node list without a lock, which could open two flow streams for one node or keep a closed node as in use. A node closed when this OAP's share of nodes moved away was reused, still closed, when the share moved back (e.g. after scaling the OAP cluster out and back in), so that node went unread while the assignment lasted. A `Receiver`-role OAP on a ZooKeeper, Consul, Nacos or etcd coordinator never finds itself in the cluster list and, when Cilium nodes and other OAPs were listed, threw on every refresh; it now skips Cilium fetching quietly, as the `Mixed` and `Aggregator` OAPs share all Cilium nodes among themselves.
* Fix the gRPC alarm hook throwing a `NullPointerException` on every alarm until OAP restart: once an alarm fired while no gRPC hook was configured (at boot, or after the hooks were removed through dynamic configuration), adding a gRPC hook later broke it. Also shut down the client of a gRPC hook removed from the configuration.
* Fix the Cilium fetcher silently stopping a Cilium node's flow stream. When a stream failed and was retried (e.g. a Cilium agent restart), the ended stream's thread interrupt stayed registered on its node, so closing that node later (e.g. when the OAP cluster scaled) interrupted whichever stream the pooled thread then ran for another node, and an interrupted stream is treated as closed and never retried. A stream that started just as its node closed was also never interrupted. Each stream now registers before it opens and deregisters when it ends, and a closed node refuses new registrations.
* Fix one gRPC alarm hook with a malformed target, such as `http://host` or `host:port` as the host, stopping every gRPC hook: building its client threw and aborted the whole gRPC callback on each alarm, and a malformed target in the static alarm settings stopped OAP from starting. That hook is now skipped with an error log, at boot too, and a hook whose target becomes malformed keeps its previous client.
* Make the cluster coordinator's watcher list safe for a watcher that registers after the coordinator started, as the Cilium fetcher does: the plain list shared with the coordinator's notify thread could throw a `ConcurrentModificationException` there or miss the new watcher.
* Add the `OTLP_VIRTUAL_GATEWAY` layer: the OTLP trace analysis draws a gateway listed in `gateways.yml` as a node of this layer, the OTLP counterpart of the agent path's `VIRTUAL_GATEWAY`, as it already puts the databases, caches and brokers it conjectures under the `OTLP_VIRTUAL_*` layers. The shipped `tal/otlp-general.yaml` uses it; a copy of the rule file made from an earlier release keeps drawing `VIRTUAL_GATEWAY` until it is updated.
* The analysis of SkyWalking agents' traces now runs as Trace Analysis Language (TAL) rules, like the OpenTelemetry trace analysis, and can be read and extended the same way. The rule files are listed in the new `trace-analyzer` setting `nativeTalFiles` (`SW_TRACE_NATIVE_TAL_FILES`) and ship under `config/tal/`. Metrics, topology and stored traces stay the same, apart from two edge cases: where a tag is looked up by its key, such as the tags kept with service and endpoint metrics, a span that repeats the key now gives its first value (and a cache span with a repeated key is now analyzed instead of failing its segment), and a segment that fails during analysis no longer sends AI evaluation samples.
* Uninstrumented gateways in `gateways.yml` now also match a bare host in SkyWalking agents' traces, as they already did in OpenTelemetry traces: an address written without a port, as an HTTP client records it when it omits the default port, matches the gateway listed at port 80 (or listed without a port), so a gateway is listed once. Port 443 is not inferred: a bare host is retried only at port 80, so a gateway configured at port 443 matches only an address that includes `:443`.
* `SW_TRACE_ANALYZER=-` now stops the OAP from starting while the native trace receiver (on by default) or the Kafka fetcher is enabled, because they need the `trace-analyzer` module to analyze agents' traces. Without either of them, it still turns off the OpenTelemetry trace analysis as before.
* The log lines of the agent trace analysis moved to new logger names, one per rule file: `org.apache.skywalking.trace.analysis.script.<file>`, such as `org.apache.skywalking.trace.analysis.script.native-rpc` for what `RPCAnalysisListener` logged. Update a logging configuration that names one of the old listener classes; the Native Trace Analysis doc lists the new names.
* TAL rules can now assign a declared variable with `=`, loop with `foreach`, write log lines with `log`, use typed layer values (`as Layer`), and limit a rule file to loaded modules with `requiredModules`; more functions, `toJson` and `toJsonArray` among them, can be called anywhere a value goes. A custom rule that uses `source`, `foreach`, `in`, `build`, `first`, `segmentDef`, `writeNetworkAlias` or `log` as a variable name has to rename it, as they are now keywords.
* TAL rules write their records with `source {}`, such as `source DatabaseSlowStatement {}`, which an OpenTelemetry rule sends where it is written. The OpenTelemetry rules' `outputType` key and `sink {}` block are removed: a custom rule file written for 11.1.0 that uses them fails to load until its record moves to a `source {}`, as the shipped `otlp-slow-sql` rule now writes its slow statement.
* AI evaluation samples natively stored OpenTelemetry spans (`otlpTraceStorage: otlp`) through the new `otlp-ai-evaluation` TAL rule, listed in `trace-analyzer`'s default `talFiles`, instead of its span listener. It is declared for the `OTLP_GENERAL` layer, like the other shipped OpenTelemetry rules, so it sees only the spans of services that set `service.layer=OTLP_GENERAL`: a GenAI application whose spans should be evaluated sets that resource attribute, for example `OTEL_RESOURCE_ATTRIBUTES=service.layer=OTLP_GENERAL`. A deployment that sets `talFiles` (`SW_TRACE_TAL_FILES`) adds `otlp-ai-evaluation` to it. Zipkin spans, and OpenTelemetry spans stored as Zipkin spans, are sampled as before.
* Fix a webhook alarm hook not being posted when the alarm also names a hook of another type: the webhook callback looked up the other hook's name in the webhook settings and threw a `NullPointerException`. Depending on the hook names, the webhook was never posted (for example `webhook.default` with `gRPC.default`), or an error was logged on every alarm.
* Add `alarm.default.grpcTimeout` / `SW_ALARM_GRPC_TIMEOUT`, the deadline in seconds of each gRPC alarm hook stream (default `10`, which was the fixed deadline before).
* Record gRPC alarm hook deliveries on the alarm delivery self-observability metrics (`alarm_http_delivery_total` and `alarm_http_delivery_latency_seconds`) with `hook_type=gRPC`, so the OAP dashboards show the gRPC hook as one more channel.
* Keep the trace an OTLP log was written in: the OTLP log receiver now stores a record's `trace_id` as the log's trace ID, which it dropped before, and its `span_id` in a new `otlp_span_id` column. The log query's `TraceScopeCondition` takes `otlpSpanId` to read the logs one OTLP or Zipkin span wrote, which the numeric `spanId` cannot name, and a LAL rule sets it with `otlpSpanId`, an output field of the default output type. An existing BanyanDB log stream and Elasticsearch log index gain the column at boot.
* A log query's `relatedTrace` is one of `traceId` alone, `traceId` with `segmentId` and `spanId` for a SkyWalking native span, or `traceId` with `otlpSpanId` for an OTLP or Zipkin span; any other mix is refused rather than read. This also refuses two forms accepted before: `segmentId` without `spanId`, which read the logs of a whole segment, and `spanId` without `segmentId`. The debugging query API refuses `segmentId`, `spanId` or `otlpSpanId` without `traceId`, which it ignored before.
* Fix OAP running out of memory when receiving Envoy metrics from a large mesh. Converting a metric name (replacing `.` and `/` with `_`) went through a cache capped at 1,000 names, but Envoy metric names embed the upstream cluster name, so a large mesh has many more of them. The cache kept missing, and every miss took a lock shared by all Envoy metrics streams; the blocked streams piled up gRPC threads until OAP ran out of memory. The name is now converted directly, without a cache or lock.
* **Breaking Change** — JDBC storage (MySQL, PostgreSQL): the log tables gain the `otlp_span_id` column, and OAP adds it at boot only to the current day's table. Every other existing log table keeps its old shape — including the next day's, when OAP had already created it before the upgrade — and inserting a log into one fails, for logs from every source. When upgrading, add the column to the existing log tables, `ALTER TABLE log_<yyyyMMdd> ADD COLUMN otlp_span_id VARCHAR(64);`, or drop them, which deletes their logs, so OAP creates them anew.
* Fix the Apollo configuration dropping items of a grouped dynamic configuration: when one item of a group changed, the others were removed from OAP until they changed again or OAP restarted, because the change listener passed on only the changed keys while the receiver treats what it is given as the whole group. The listener now reads the whole group again.
* BanyanDB: fix the instance hierarchy query, which read the service hierarchy measure and failed with `fail to query measure`, so an instance's hierarchy never loaded.
* BanyanDB: fix alarm paging without an entity filter: the offset was applied in the query and again to its result, so every page after the first came back empty.
* BanyanDB: fix the eBPF profiling analysis reading at most 100 rows of a schedule per 10-second window, and counting a row uploaded on a window's end in both windows. It now reads every row of `[begin, end)`, as Elasticsearch and JDBC do.
* BanyanDB: fix trace profiling's thread-snapshot reads. A batch included its upper sequence, so the analysis counted a snapshot on a batch boundary twice; a snapshot lost its language, so a Go profile read back as Java and the Go analysis found nothing; and an empty range returned the integer extremes instead of `-1`.
* Fix a trace-profiling thread snapshot's time bucket being narrowed to `int` when read back, which overflowed for any second-level bucket.
* BanyanDB: fix the process counts of the eBPF profiling pages counting distinct property sets instead of processes, and the service process count ignoring its end time.
* Fix two Zipkin query bugs on Elasticsearch and OpenSearch. A Zipkin search that matched nothing, and a `traceMany` lookup of unknown trace IDs, left a scroll context open on every shard of the Zipkin span indices until its 30-second keep-alive ran out; enough of them within that time pass the server's `search.max_open_scroll_context` (500 by default), and every scroll search on the server then fails with HTTP 429. With custom routing on (`SW_STORAGE_ES_ENABLE_CUSTOM_ROUTING`), a Zipkin search that matched nothing failed with HTTP 400 instead of returning no traces.
* BanyanDB: fix the span-attached event query (`ISpanAttachedEventQueryDAO`) failing on every call with `fail to query stream`. It read `sw_span_attached_event_record` and `span_attached_event_record` streams that BanyanDB never has: since the trace model of 10.3.0, the events eBPF profiling attaches to spans are written into the `segment` and `zipkin_span` traces, as spans of their trace. It now reads them there, every event of the traces asked for, in start-time order to the nanosecond, as Elasticsearch and JDBC return them. The trace and Zipkin query services read these events together with the trace on BanyanDB and do not call this query, so no page showed the failure.
* BanyanDB: fix a persistence round that writes the sampled slow database statements (the TopN records, once every `topNReportPeriod`, 10 minutes by default) waiting up to `flushInterval` (15 seconds) for the stream bulk to send them. `endOfFlush` sent only the round's metrics, on the belief that the persistence timer writes no stream, and the timer starts the next round only when a round is answered, so that round and the start of the next were held back. `endOfFlush` now sends the queued stream writes too, as the Elasticsearch storage sends its whole bulk, and sends each bulk even when the other's batch fails.
* BanyanDB: fix dropping a measure, as removing a runtime rule or changing a metric's function with `allowStorageChange` does, leaving its pre-built TopN aggregations behind on the dropped measure. The drop deleted a TopN aggregation named after the measure, but each is named after its `bydb-topn.yml` rule, so none was deleted, and a measure created again under the same name found the old ones in place and kept their old definition. It now deletes every TopN aggregation whose source is the dropped measure, and when one fails to delete it stops before the measure, so the removal fails and is tried again instead of leaving that aggregation behind.
* Fix the trace and Zipkin queries putting an event of eBPF profiling on the wrong span, or losing it. A server-side event (a request read, or a response written, on the server, attached to the client's span through its trace context) belongs on the server's span, while the client-side events of that span stay on it; but the span an event went to was remembered by the span the event named alone, so every event of a span followed its first one. On a Zipkin trace, a span that took both its own events and the server-side events of its client span was also rebuilt twice, keeping only one of the two sets. Each event now goes to the span of its own side.
* Fix span-attached events of eBPF profiling overwriting each other. An event's storage ID was its segment ID, start time and name. Rover sends a Zipkin event with an empty segment ID, so two Zipkin events with the same name and start time, in any two traces, had one ID, and so could two SkyWalking events on different spans of one segment. Elasticsearch kept only the one written last, and JDBC, whose row key is the same ID, cannot hold both. The ID now also carries the trace ID and span ID.
* Fix JDBC trace profiling queries failing when a task has no profiled segments: the empty segment-ID list now returns an empty result without generating an invalid SQL `IN ()` clause.
* Add the `query-server` module, so the native query APIs can have their own port, apart from the ports agents report to. Set `SW_QUERY_SERVER_REST_PORT` to a port greater than 0, and GraphQL (`/graphql`), the AI agent conversation view and files (`/ai-agent/conversations/*`), and `/status/config/ttl` move from the core REST port (default `12800`) to it, with their own host, context path and TLS settings (`SW_QUERY_SERVER_REST_*`). Point the UI's `queryUrl`, `swctl --base-url` and other GraphQL clients at the new port. With the default `0`, nothing changes. Together with `receiver-sharing-server`, no agent or query traffic is left on the core ports.
* LAL: save the logs of the OpenTelemetry services that set `service.layer=OTLP_GENERAL` through the new `otlp-general` rule in `lal/default.yaml`; no rule matched that layer, so these logs were dropped. A LAL rule declaring an unregistered or missing layer (names are case-sensitive) is now skipped with a warning at boot and rejected when applied as a runtime rule, instead of loading silently under `UNDEFINED` and never running.
* LAL: a log without a layer that no `layer: auto` rule claims runs the new `fallback: true` auto rules, instead of the rules declared for `GENERAL`, and is dropped when none claims it either, so where such a log is filed is decided by a rule, not hard-coded. The new `default-fallback` rule in `lal/default.yaml` files it under `GENERAL`, as before; edit its extractor to file it under another layer. A fallback rule must set the layer, as any auto rule. A custom `layer: GENERAL` rule written for the logs without a layer must declare `layer: auto` and `fallback: true` and set `layer "GENERAL"` in its extractor; it then runs next to `default-fallback`, as it ran next to `default` before. The OAP warns at boot when no `fallback: true` rule is loaded, and when a runtime rule change removes the last one, since the logs without a layer are then dropped with only a debug log each.
* LAL: handle the mini-program error logs with the `miniprogram-errors-wechat` and `miniprogram-errors-alipay` rules in `lal/miniprogram.yaml`, declared for the `WECHAT_MINI_PROGRAM` and `ALIPAY_MINI_PROGRAM` layers, replacing the `layer: auto` rule `miniprogram-errors`. The mini-program SDK v0.5.0 sets `service.layer`, which routes its error logs to these rules; it is now the minimum supported SDK version, since an older SDK's error logs carry no layer and are filed under `GENERAL` without the `error_count` metric.

The log query accepts a key of either list. The rules shared the log's metadata, so a `layer` statement in one rule changed the layer of the rules that ran after it on the same log, depending on the order the rules ran in, and an invalid layer from one rule made the next one fail; each rule now runs on its own copy of the metadata. An auto rule with a `sink` but no `layer` statement, which dropped every log it saved, is now skipped with a warning at boot and refused as a runtime rule; one without a `sink` needs no `layer` statement. In any LAL rule, a `layer` statement that evaluates to an empty, null or unregistered layer now drops the log with a warning when it is saved, where the traffic sink threw for it and lost the log with only a stack trace.

* Fix a LAL rule applied through the runtime-rule API being attributed to `lal/lal/<name>.yaml`, the catalog prefix applied twice, in its error messages and its generated class; it is now `lal/<name>.yaml`, as the same file loaded at boot.
* Log tag autocomplete keeps the tags of the logs received through OTLP apart from those of every other source, under the new tag type `OTLP_LOG`. `queryLogTagAutocompleteKeys` and `queryLogTagAutocompleteValues` take an optional `type` (`LOG` or `OTLP_LOG`) to read one source; without it, as the UI and LogQL query, they return both merged, within the same limit. Both are read in one storage query: `ITagAutoCompleteQueryDAO` takes a list of tag types, so a storage plugin outside this repository that implements it has to follow.
* DSL engines (OAL, MAL, LAL, TAL, hierarchy rules), with three goals. (1) Fail explicitly and loudly: a part of a rule an engine silently dropped, rewrote or misread now fails the rule's compilation with a message naming the rule and what it does not support; at boot that stops the OAP, and a runtime-rule update is rejected. (2) One set of operators and conversions: `==` (lists, arrays, sets, maps and JSON values by content, a string against a number as the number it holds), the orderings, `+` with a string (a text joins only onto a text, a number, a character or null, and never with an array, a collection or a map), the whole-number quotient, octal literals and an array's `toString()` follow one rule across the engines, from shared helpers in server-core, and each engine calls only the Java its documentation lists, kept in one shared allow-list structure (`DslCallables`). (3) No feature or expression regression: every shipped rule and every documented form compiles and computes as before; what changes is a form that was silently wrong, which now fails or computes as written (the entries below name the shipped rules affected), and a Java call outside an engine's documented list, which is refused.
* OAL, MAL, LAL and hierarchy rules: a character no token matches fails the compilation, where the lexers dropped it and compiled the rest (OAL `filter(latency >= -100)` compiled as `>= 100`, and a line starting with `#` stayed active).
* MAL: closures run as v1 (Groovy) ran them where v2 differed (ternaries, operator precedence and associativity, Groovy truth in filters, whole-number quotients as Groovy's `BigDecimal`, octal literals, negative indexes, `${...}` in closure strings), and a form v2 compiled while dropping part of it fails the compilation; see mal.md. The `otel-rules/aws-gateway` service falls back to `ApiName` when `ApiId` is empty; the instances of `otel-rules/k8s/k8s-instance`, `otel-rules/banyandb/banyandb-instance` and `otel-rules/process-hostmetrics-{linux,windows}` carry only the properties their closures return, not every label; a sample a rule file's `filter` fails on is dropped, where the batch passed unfiltered; `metric * -1` is a scalar operation, where it gave EMPTY.
* Hierarchy rules: `else if`, braced branches, `!`, `a - b + c`, boxed numbers and parameters named `arg0`/`arg1` compile as they read, where v2 compiled something else, and a form it cannot run (`!a == b`, a block that can end without `return`, interpolation in a double-quoted string) fails the compilation; see service-hierarchy-configuration.md.
* LAL: the v2 compiler runs a rule as Groovy LAL did, or fails its compilation naming what it does not support, where it dropped or rewrote parts (an `abort {}` in an extractor's `if`, a nested `if` in a sink, method chains after `tag()` and the other functions, casts, the order of samplers); lal.md lists the differences from Groovy LAL that v2 keeps. `as Boolean` converts a boolean, the text `true` or `false` in any case, and a number or a text holding one by zero (0 false, any other true), and fails the log on any other value (`"yes"`). A standard field statement (`service`, `instance`, `endpoint`, `traceId`, `segmentId`, `spanId`, `timestamp`) also sets what later reads of the log and the traffic it builds see: `lal/nginx.yaml`'s error-log metric takes the parsed time, `lal/miniprogram.yaml` builds instance and endpoint traffic and `lal/ios-metrickit.yaml` instance traffic, the slow-SQL rules' service traffic uses `parsed.service`, and the network-profiling rules of `lal/k8s-service.yaml`, `lal/mesh-dp.yaml` and `lal/envoy-als.yaml` write no sampled trace for a log without its `client_process` or `server_process`; `lal/ios-metrickit.yaml` aborts, as written, a log whose `name` tag does not start with `metrickit.diagnostic.`.
* OAL: a script that compiled into something other than what it says now does what it says or fails the compilation with its source location: statements after a stray token or an unterminated comment were dropped, surplus or missing function arguments were ignored or reached another overload, string, escape, `100L`, `1_000` and `in [...]` literals were misread, a comparison across types, a `like` without `%`, an out-of-range number and a double passed to a long parameter matched or computed wrongly, and `percentile2(0)` and `histogram(0, ...)` failed every event. A generated class the JVM verifier rejects fails the compilation instead of the boot, and a from() attribute no function reads or a `disable(...)` naming no stream, or one already defined outside `disable.oal`, is logged as a warning; see oal.md.
* TAL: a rule runs as written or fails its compilation naming what is wrong, where parts of it were dropped, replaced or read as something else (a repeated `metrics {}` clause or tag key, an unknown type after `as`, a misspelled layer, a method on a literal, a `log` argument beyond its placeholders), and two rules of one name, or two candidate files for one listed name, fail the boot. Values evaluate as LAL's: a cast that does not convert fails the span, conditions use Groovy truth, a whole-number quotient stays exact until its destination converts it (the shipped nanosecond-to-millisecond conversions are unchanged), and a leading-0 integer is octal; see tal.md. The shipped `otlp-general` `attr(...) as Double >= 400` fails a span whose status code is text that is no number, and a padded native `transmission.latency` tag reads where the Java analyzer failed the segment.
* Fix the Redis instance `meter_redis_instance_average_time_spent_by_command` showing 0 or 1 instead of the average time of a command. The rule divided the two lifetime counters `redis_commands_duration_seconds_total` and `redis_commands_total` first and took the rate of that ratio, which is how fast the lifetime average drifts. It now divides the rate of the command time by the rate of the command count, and reports `0` for a command that did not run in the window. The metric is now in microseconds, not seconds: a meter value is stored as a whole number, so an average below 1 second was stored as 1. Values stored before the upgrade keep the old numbers.
* Add self-observability metrics to the OTLP trace receiver, following the agent and Zipkin trace receivers. The OTLP histogram `otel_spans_latency` is replaced by the shared `trace_in_latency` with `protocol` `otlp-grpc` or `otlp-http`, observed once per span instead of once per export request, as the span's latency × 1,000, like the Zipkin protocols; so the OTLP spans show in `meter_oap_instance_trace_count` and `meter_oap_instance_trace_latency_percentile` by protocol. `meter_oap_otel_spans_received` is kept, now summed from `trace_in_latency` over the two OTLP protocols, and counts spans, where it counted export requests; `meter_oap_otel_spans_latency_percentile` is removed. An alarm, dashboard or Prometheus query built on `otel_spans_latency` or the removed meter must move to `trace_in_latency{protocol=~"otlp-.*"}` or `meter_oap_instance_trace_latency_percentile`, with new thresholds. New counter `otel_spans_rejected`, the spans of a resource without a service name, which were only reported in `partial_success`. The OTLP counter `otel_spans_dropped` is replaced by the shared `spans_dropped_count` with `protocol` `otlp-grpc` or `otlp-http` and a `reason` (`sampled`, `rate_limited`, `store_failed`, `process_failed`), and now also counts spans lost to a processing error, which were only logged; in Zipkin mode the spans the Zipkin receiver drops are counted under the OTLP protocol with their own reason. `meter_oap_otel_spans_dropped` is kept, summed from `spans_dropped_count` over the two OTLP protocols; a Prometheus query on the raw `otel_spans_dropped` must move to `spans_dropped_count{protocol=~"otlp-.*"}`. Failed export requests count in the shared `trace_analysis_error_count` with `protocol` `otlp-grpc` or `otlp-http`. The MAL rules add `meter_oap_otel_spans_rejected`. One span that fails to be processed no longer discards the rest of its resource's spans.
* `trace_in_latency` is observed once per span, as the span's latency × 1,000, because one span takes microseconds, below the smallest histogram bucket (5ms); every protocol now shares this one unit. The SkyWalking agent protocols (`grpc`, `http`, `kafka`) observed once per segment: a segment is still processed as a whole, so each of its spans is observed at the segment's latency divided by its span count; a segment without spans, which the analysis discards, is not counted. The Zipkin protocols (`zipkin-http`, `zipkin-kafka`) observed once per HTTP request or Kafka message. So `meter_oap_instance_trace_count` counts spans, where it counted agent segments and Zipkin requests or messages, and `meter_oap_instance_trace_latency_percentile` is the milliseconds 1,000 spans take; an alarm or dashboard built on either needs new thresholds. Decoding the request or message is no longer in it, nor are the Zipkin spans dropped by sampling or the rate limit; the agent HTTP `/v3/segments` endpoint is timed per segment instead of per request. `SpanForwardService.send` takes the histogram to observe each span into. The Grafana dashboards rename the "Trace Segment" panels to "Trace Span", and the error-count panel to "Trace Analysis Error Count" since it also counts failed Zipkin and OTLP requests; the trace and OTLP span latency panels are labelled "per 1,000 spans"; a "Trace Spans Dropped" panel shows `spans_dropped_count` by protocol and reason, and the OTLP spans panel adds the rejected spans; and the hourly and daily received-count panels count the spans of every protocol, where they filtered on `grpc` and a `kafka-fetcher` protocol that the Kafka fetcher never reported.
* The Zipkin receiver counts the spans it does not store in `spans_dropped_count` with a `reason` label beside `protocol`, shared with the OTLP receiver: `sampled` (`sampleRate`), `rate_limited` (`maxSpansPerSecond`) and `process_failed`. It counted only `zipkin-http`, with no reason, and now also counts `zipkin-kafka`; a Prometheus query on the raw metric that does not sum over `reason` sees one series per reason. The new MAL rule `meter_oap_instance_spans_dropped_by_reason` breaks `meter_oap_instance_spans_dropped_count` down by reason. One Zipkin span that fails to be processed is now dropped, logged and counted as `process_failed` alone, where it stopped the rest of its HTTP request or Kafka message from being processed: the HTTP request then failed and counted in `trace_analysis_error_count`, so a client retrying it stored the spans before it twice, and the Kafka message was lost without a log. `SpanForwardService.send` takes the protocol's `TraceSpansDropped` and returns nothing. Every trace receiver registers `trace_analysis_error_count` with one help text, which says what it counts: received trace data that could not be decoded or processed as a whole, an agent segment, a Zipkin HTTP request or Kafka message, or an OTLP export request; a span dropped on its own is counted in `spans_dropped_count` instead.
